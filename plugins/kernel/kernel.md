# Kit rules (apply to every task in every repo)
- Evidence: never invent data, versions, prices or results. Label estimates and inferences. Check current docs before writing integration code.
- Fail loud: if you cannot reach, read or run something you need, say so at the top and stop that part. Never fill the gap with proxy data presented as real.
- Git: work on a branch, open the PR as a draft, never push to main/master, never deploy to production from the CLI. Merge rule: once CI and merge-gate are green, mark your own PR ready and squash-merge it (never `--admin`, `--auto`, merge or rebase commits). If it touches payments/Stripe, sign-in/auth, kids' data/COPPA, database migrations, secrets/env, or deletes data, add `- [ ] Owner go-ahead to merge (touches <kind>)` under "## Needed from the owner" and merge only after the owner's go-ahead naming that PR; never tick that box yourself. A revert or prod error from an agent merge goes in the weekly ledger; if reverts climb, this rule tightens. The guard hook enforces the push, deploy and squash-only parts. Small scoped commits; no layout/content changes inside a mechanical fix.
- Sweeps: a change bound for more than one repo lands on one canary repo first, merged and checked live (the deployed site, or green CI on `main` where nothing deploys), before any other repo gets it. A sweep against a fixed outside target (a security advisory, a vendor deprecation) may go out at once; a sweep against a decision still being made (wording, naming, a policy) waits until that decision is frozen. If the canary needs a fix, fix the plan before fanning out. Rule Ratchet waves already work this way.
- Fail closed by construction: anything needing a secret or config denies when it is missing; auth allowlists public routes; rate-limit auth routes.
- Verify before "done": run the repo's build, type-check and tests, and exercise the change at runtime where possible. Then have the `reviewer` sub-agent (fresh context) check the diff against the task before opening the PR.
- Delegation: give sub-agents only their slice. Use `gatherer` for read-only research; only the main session delivers (PRs, messages, publishing).
- Stop rule: at most 2 fix-and-recheck rounds per failure; then stop and report what still fails.
- Fast-changing facts (model choices, IDs, scopes, tool picks) come from the kit's registry.yaml, not from memory or old instructions. If an entry is flagged stale, re-verify it.
- Writing anything for the owner: don't name the owner; no real names, emails, phones or handles (fake test accounts); blockers go under "## Needed from the owner".
- Handoff: at start, read `HANDOFF.md` and `.handoff/<branch>.md` (if present) and restate the goal and next step; update and push the branch file before any risky step, after every 3 finished items and before stopping; never drop a DON'T line without the owner's go-ahead.
- End substantive work with one status line: done / done-but-one-step-left / blocked-on-me.
